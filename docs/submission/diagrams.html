SpendSeal Agent 花钱时的强制执行点，在合约里

行业已经铺好了身份、支付轨道、授权证据三层。缺的是第四层—— 付款那一刻，由谁按主人的规矩说“不”。 我们把这一层从厂商服务器搬进合约：钱不在 Agent 手里，在金库合约里。

链 Monad testnet · 10143 金库池 0xc3cd…963c 资产 USDC（Circle 测试网） 测试 17 + 10

01 架构：谁在哪一侧

整套设计的起点是一条边界：Agent 所在的环境默认会被攻陷，主人的签名设备不会。 所以管理权和用钱权必须分处两个信任域，而强制点只能落在两者之外的第三个地方——合约。

不可信域假定会被攻陷
  • Claude Desktop 与模型上下文
  • MCP 桥进程（持有 agent 私钥）
  • 卖家 API 与本机网络路径
这一域里的一切都可能被提示注入、被偷、被替换。设计上不依赖它守规矩。
可信域只有它能改规矩
  • 主人钱包（MetaMask / 硬件钱包 / 多签）
  • 改限额、加白名单、熔断、提款
Agent 的工具面里没有这些操作——不是被禁止，是不存在。

02 一笔付款走六步

六步不是凑完整，是这笔交易里有两个互不信任的主体：买家要知道价、不被骗价、按规矩付； 卖家要确认真收到、且只发一次货。每一步堵一个具体的洞。

  1. 01

    卖家报价：HTTP 402 + 结构化发票

    链下

    Agent 不知道付多少、付给谁、什么币、哪个合约、何时过期——发票一次给全。

    只能盲转，退回“裸钱包 + 一句口头报价”。

  2. 02

    验签：EIP-712，签名者必须等于收款方

    链下

    防中间人改金额、换收款地址。改一个字，签名立刻失效，交易根本不发出。

    篡改发票、钓鱼发票全拦不住——Agent 在盲签。

  3. 03

    链上预检 checkPay

    可省 · 不是安全防线

    省 gas（必然失败的交易不上链）、给 Agent 结构化的失败原因、触发拒绝上链审计。

    安全不变（合约照样会拒），但白付 gas、Agent 只能从 revert 里反推、大屏拦截计数没数据。

  4. 04

    付款 tryPay：合约逐条校验

    链上 · 核心

    存在 → 未熔断 → 未过期 → 白名单 → 单笔限额 → UTC 日累计 → 余额。任一不过就拒。

    整个项目失去意义：Agent 可以超额、付给任何人、泄露后任意花。

  5. 05

    卖家验付：按 PaymentExecuted 事件核对

    链上

    核对收款方、金额、发票绑定的 ref——三者对上才发货。

    卖家只能信 Agent 的口头话：少付、拿别人的交易来骗货都拦不住。

  6. 06

    发票 nonce 一次性消费

    链上

    一张发票只能兑付一次；同一笔交易重放，直接 nonce_already_consumed。

    一笔 0.05 USDC 可以无限次白嫖同一份截图。

诚实边界：哪一步可以省 第 ③ 步严格说可以省——安全边界在合约，不在预检。它的定位是经济性 + 可解释性 + 审计，不是防线。 真正不能少的是四步：报价（知道价）、验签（不被骗价）、合约校验（按规矩付）、验付 + 防重放（确认真收到、只发一次货）。 缺一个，买卖闭环就断。

03 团队预算池：一个池子，多张卡

前面的金库守一个 Agent。团队要给一批 Agent 发预算，问题就变成两个：钱共享，但账要分开；谁也不能把全队的额度吃光；超额不能由机器自己决定。

04 六步覆盖率：谁做了哪几步

单看每一步，几乎都有人做过。但把六步放进同一个能买到东西的闭环，并且把强制点只放在合约里——这是我们检索后未见完整同款的部分。

按付款六步逐项打点
步骤 普通支付 官方 x402 生态 服务器侧护栏
Circle / Coinbase / AP2		 本项目
① 402 报价 ✕人要看见收银台 ✓ ◐部分支持 ✓
② 卖家签报价 + 买家付款前验签 ✕靠 TLS ✕签的是支付授权，不是报价 ✕靠 TLS ✓签名者必须等于收款方
③ 链上预检 ✕ ◐客户端 ◐服务器检查 ✓
④ 合约内逐条校验 ✕平台/发卡方执行 ✕规格无预算字段 ✕在厂商服务器上执行 ✓唯一的无服务器执行
⑤ 事件验付 ◐事后对账 ✓ ◐ ✓
⑥ 防重放 ◐ ✓ ◐ ✓
读法（三句话，台上够用） ①⑤⑥ 是 x402 生态的成熟件，我们不声称发明；④ 在 Sentinel（EIP-7702 账户级）和 KeeperCard（ERC-7710 caveat）身上也见过无服务器版本，那是我们设计上的参照与致敬。 真正没有同款的是 ②：卖家对这张报价签名、买家桥在付款前先验签——别人签的是结算授权或协议授权，不是报价。
为什么 ② 是这六步里最关键的一步 合约看到的只有 (payee, amount, ref)，它看不到报价。所以护照的每一条规则都可能全部通过，而付的是一张被改过的假发票—— 这就是“盲签”。②把报价在源头用密码学签死，这是六步里唯一把“信任网络”换成“信任数学”的一步。

05 为什么非做不可

不是“未来可能需要”，是三件已经发生的事：规矩放错地方已被实验证明失效，责任已经划给用户，钱已经在以亿笔量级流动。

结论 当责任无法在事后安放时，事前在付款时刻拦住，就是唯一的损失边界。 普通支付把它交给人，官方 x402 把它交给生态（而生态把它交给服务器），我们把它交给合约。

06 适用领域：什么时候该用，什么时候不该用

这套设计不是所有 Agent 支付的最优解。它在四个条件同时成立时才有价值；否则有更简单、更便宜的选择。

台上口径边界（说错会被懂行的评委纠正）

  • 不说“首创 / 第一个做链上强制”——ERC-7710 本身就是链上强制；我们的增量是组合与强制层级。
  • 不说“管控层是空白”——限额产品不空，缺的是跨厂商累计 + 无信任执行 + 主人自助撤销。
  • 不说“$25B 是 Monad 上的量”——那是 Visa 全网年化量；Monad 是被纳入结算网络名单。
  • 不报两个终局数字（400ms / 800ms 口径不一）——只说“亚秒级终局”。
  • 不把 x402 生态说成我们的发明——①⑤⑥ 是成熟件，我们补的是 ② 和“强制点只在合约”。
  • x402 修正后的真实量有两个版本（1,500 万 / 1,900 万），无法赛前核实——只说“千万美元级”。
